# 阶段 2 学习日志：我的工单

## 1. 这一阶段解决什么问题

早期项目里，员工只能在 Agent 对话中说“查看我的工单”，系统把结果作为一段文本返回。它能证明 Agent 会调用工具，却不适合真实工作：员工不能按状态筛选、不能搜索历史问题，也难以快速打开某一张工单确认提交内容。

这一阶段把工单变成独立的员工工作入口。员工可以在“我的工单”页面查看自己提交的请求，按生命周期状态筛选，按标题或问题描述搜索，通过分页浏览记录，并点击列表项查看工单摘要。

## 2. 员工可以完成的操作

- 在侧边栏打开“我的工单”。
- 临时切换当前操作人，查看该员工自己的数据。
- 在“全部、待受理、处理中、已解决、已关闭”之间筛选。
- 用关键词搜索工单标题和问题描述。
- 使用上一页和下一页浏览较长的历史记录。
- 点击某张工单，查看优先级、状态、提交时间、最后更新时间和问题描述。

当前页面没有让员工直接修改状态，也没有显示处理评论、附件和处理人。这些属于下一阶段的工单协同能力，不能用前端假数据代替。

## 3. 后端接口如何设计

新增两个只读接口：

```http
GET /api/v1/tickets?status=open&query=VPN&limit=10&offset=0
X-Actor: alice

GET /api/v1/tickets/{ticket_id}
X-Actor: alice
```

列表接口返回的不是数组，而是一个分页对象：

```json
{
  "items": [],
  "total": 0,
  "limit": 10,
  "offset": 0
}
```

这样前端才知道是否还有下一页，也可以显示匹配总数。分页逻辑使用 `limit` 和 `offset`：例如每页 10 条，第二页就是 `limit=10&offset=10`。

## 4. 数据隔离是怎么做到的

所有工单读请求都从 `X-Actor` 取得当前员工，并在数据库查询中强制追加：

```text
Ticket.requester == actor
```

也就是说，筛选、搜索、计数和按 ID 读取都在同一个“当前申请人”范围内执行。即使 Bob 知道 Alice 的工单 ID，请求 `GET /tickets/{alice_ticket_id}` 仍会得到 404，而不是拿到别人的问题描述。

这里的 `X-Actor` 仍只是演示身份。生产环境需要由登录态、组织成员关系和角色权限提供真实身份；但把隔离条件放在仓储层和服务层的做法可以直接复用。

## 5. 搜索为什么在数据库中完成

`TicketRepository` 根据关键词构造：

```text
lower(title) LIKE '%关键词%'
OR lower(description) LIKE '%关键词%'
```

这是一种适合当前 SQLite 与 PostgreSQL 开发阶段的可移植基础搜索。它避免把所有工单读到 Python 内存再过滤，也让总数统计和列表查询使用同一套条件。

当工单量更大、需要同义词、分词或排序评分时，可以把工单搜索接入 Elasticsearch；但那应该是经过压测和产品需求确认后的升级，而不是现在为了“看起来高级”而增加一套不一致的数据源。

## 6. 前端怎样和接口协作

前端维护一小段页面状态：当前状态筛选、关键词、每页数量、偏移量、总数和当前选中的工单 ID。用户改变筛选或搜索词时重置 `offset=0`，避免还停留在旧搜索结果的后续页；点击工单后，前端再次按 ID 请求详情，而不是完全相信列表摘要。

详情数据使用 DOM 的 `textContent` 渲染，没有拼接 `innerHTML`，因此工单描述中的内容不会被浏览器当作可执行 HTML。

## 7. 本阶段如何验证

新增 `tests/test_ticket_api.py`，覆盖以下事实：

1. Alice 和 Bob 创建同名工单后，Alice 搜索时只能得到自己的记录。
2. 关键词搜索会返回正确的总数与记录。
3. `limit=1` 时，第一页和第二页是不同记录。
4. Bob 请求 Alice 的工单详情时返回 404。

同时运行前端脚本语法检查和完整 pytest 套件，确保新增页面没有影响既有 Agent、知识库和索引功能。

## 8. 面试时可以怎样介绍

> 我把 Agent 中的工单工具从单次对话能力扩展成了独立的员工工单中心。后端用分页读模型返回列表和总数，筛选、搜索与计数复用同一组数据库条件；更重要的是，所有读取都把当前员工身份作为强制查询条件，按 ID 访问别人工单也会返回 404。前端只展示真实已落库的数据，并把状态流转、评论和附件留给下一阶段，避免先用静态交互造成“看起来可用、实际没有业务闭环”的问题。
