# 阶段 19 学习日志：离线评测体系

## 1. 为什么功能演示不够

知识库问答、混合检索、GraphRAG 和 Function Calling 在页面中“能跑通”，只说明一次演示没有报错。它不能证明检索比单一方案更好、模型是否稳定选择正确工具，也不能证明安全约束在不同请求下持续生效。

离线评测把这些问题转换成固定的、可重复执行的用例。每轮更换模型、Embedding、RRF 参数或重排器后，都在相同的 gold 集上运行并保存结果，才能进行公平比较。

## 2. 本阶段新增了什么

- 版本化 gold 集：`docs/evaluation/knowledgeops-gold-v0.1.json`。
- 脱敏的企业支持资料：`docs/evaluation/fixtures/`。
- 检索指标：`Recall@k`、`MRR`、`nDCG@k`、平均/P50/P95 延迟。
- Function Calling 指标：工具选择准确率、参数有效率、建单草稿确认门禁通过率。
- 安全门禁清单：未确认建单、跨员工读取、无服务台角色操作。
- 运行脚本：`scripts/run_offline_evaluation.py`，输出 `report.md` 和 `report.json`。

## 3. 为什么要同时保存 Markdown 和 JSON

Markdown 适合阅读、汇报和面试展示；JSON 保存机器可读的原始指标，后续可以画趋势图、在 CI 中设置质量门禁，或比较不同模型配置。两者由同一次运行写出，避免手工抄录数字造成不一致。

## 4. 什么是公平对比

比较 `vector`、`bm25`、`hybrid`、`hybrid_rerank` 和 `graph` 时，必须使用同一批已索引文档、同一个知识库 ID、相同的查询集和相同的 k 值。否则更高的分数可能只是因为某个方法使用了更多资料或不同的模型，而不是方法本身更好。

在 v0.1 中，gold 集使用 `source_name` 作为证据标识，便于导入演示资料后稳定匹配。实际企业版本应逐步标注到具体 `chunk_id`，从“找到正确文档”提升到“找到正确片段”。

## 5. Function Calling 为什么可以离线评测

评测只调用模型的第一轮，并检查它返回的工具名称和 JSON 参数。例如“查看我的工单”应选择 `list_my_tickets`，“创建 VPN 报修”应选择 `prepare_ticket_draft`。它不会执行工具，因此不会查询真实工单，也不会产生写入。

这把“模型会不会正确用工具”和“系统是否安全执行工具”拆开：前者由离线模型评测衡量，后者由 API、服务层和 LangGraph 的集成测试作为零容忍门禁验证。

## 6. 当前边界

v0.1 提供的是可运行的评测基础设施和脱敏演示 gold 集，不能替代真实企业语料的评测结果。项目尚未生成任何性能或准确率数字；报告在实际运行前明确显示 `TBD`。

## 7. 面试时如何介绍

> 我没有把 RAG 和 Agent 只当作功能 Demo，而是建立了版本化的离线 gold 集。检索层同时评估召回、排序和 P95 延迟；Agent 层在不执行真实业务动作的前提下评估 Function Calling 的工具选择与参数质量；工单的未确认写入和越权访问则作为零容忍安全门禁。每次评测会同时输出 Markdown 和 JSON，因此结果可复盘、可比较，也可以接入 CI。
