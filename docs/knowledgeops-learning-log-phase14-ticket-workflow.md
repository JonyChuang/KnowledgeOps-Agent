# 阶段 14 学习日志：工单状态流转与处理闭环

## 1. 这次补了什么

之前的“我的工单”页面能够按“待受理、处理中、待我补充、已解决、已关闭”筛选，但详情侧栏没有改变状态的操作，因此这些标签只是查询条件，不能形成业务闭环。

本阶段在详情侧栏增加了随状态变化的操作按钮：

1. 待受理：`受理并开始处理`，进入处理中。
2. 处理中：`请求补充信息`，进入待我补充；或填写处理结果后`标记为已解决`。
3. 待我补充：员工填写补充信息后自动回到处理中；演示时也可以点击“继续处理”。
4. 已解决：员工可`确认解决`，进入已关闭；或`重新打开`回到处理中。
5. 已关闭：不再显示处理操作，避免结束后的工单被随意修改。

## 2. 为什么不能让前端直接改标签

状态不是一个单纯的页面显示字段。前端直接修改颜色或文字，刷新页面后就会丢失，也无法留下谁在什么时候处理过的记录。

因此前端调用 `POST /api/v1/tickets/{ticket_id}/status`，后端由 `TicketService.transition_status()` 校验允许的下一步，再把状态写入 `tickets.status`。每次成功流转还会向 `ticket_activities` 和审计表追加一条事件，详情页的时间线据此展示操作原因和状态变化。

## 3. 状态机规则

```text
待受理 -> 处理中 -> 待我补充 -> 处理中 -> 已解决 -> 已关闭
                     \-----------------------> 已解决
已解决 -> 处理中（重新打开）
```

后端拒绝不在这张图里的跳转，例如不能将待受理直接关闭，也不能把已关闭工单重新改成处理中。这种校验必须留在服务端，不能只依赖页面是否显示按钮。

## 4. 演示环境与真实落地的差别

目前项目仍使用 `X-Actor` 作为临时身份，所以同一个演示账号既能提交工单，也能演示服务台受理、请求补充和解决操作。这样可以完整测试工单闭环。

真实企业版本应接入登录、角色和队列：员工只能补充、确认解决或重新打开自己的工单；服务台成员才能受理、分派、请求补充和标记解决；管理员负责 SLA、分类和权限配置。状态机接口可以保留，只需把现有的“工单归属校验”扩展为“工单归属 + 角色权限校验”。

## 5. 如何向面试官介绍

> 我把工单状态设计成由后端约束的状态机，而不是由前端随意切换标签。每次流转既更新当前状态，也向活动表追加不可变的审计记录，所以用户在详情中可以看到问题从受理、处理、补充到解决的完整原因链。为了便于本地演示，临时身份可以跑完整闭环；生产环境则会把各个状态动作绑定到员工、服务台和管理员角色。
