# 阶段 12 学习日志：Agent 交互边界与首轮对话体验

## 1. 这次解决了什么问题

员工在“我的工单”中选中一张工单时，界面同时保留了“选择一张工单”的空状态和真实详情。原因是 HTML 的 `hidden` 属性被空状态的 `display: grid` 样式覆盖。修复后，JavaScript 同时维护 `hidden` 属性和 `is-hidden` 类，CSS 再以 `display: none !important` 作为最终保护，因此两种状态必然互斥。

Agent 首次提交消息时，以前页面还没有真实的 `conversation_id`，前端会先显示欢迎页，再在下方追加“Agent 正在处理”。现在前端会立即创建仅在本次请求期间使用的临时会话，先显示员工消息，再显示处理中状态；服务端返回真实会话 ID 后，临时会话会被替换为已持久化的完整对话。这样界面状态与员工的操作顺序一致，失败时也能保留已输入的内容和错误提示。

## 2. Agent 的产品定位

这个 Agent 不是只能查询知识库的聊天框，也不是没有边界的通用闲聊机器人。它的定位是“企业知识与服务协同助手”，目前有四条受控能力路径：

1. `knowledge_qa`：员工提出明确的资料、规范、流程或排障问题时，在已选知识库内检索，并基于引用生成回答。
2. `ticket_query`：查询当前操作人的工单、状态和进度。
3. `ticket_create`：准备建单内容，但必须由员工再次确认后才真正写入工单系统。
4. `general_chat`：用于问候、能力说明和需求引导，不检索知识库、不调用 Chat 模型、不执行工具操作。

因此“你好”不会被误解为知识库问题，也不会出现“VPN 资料未覆盖”的无关提示。真正的问题描述进入哪条路径，仍由确定性规则和可选的 Chat 模型路由共同判断。

## 3. 为什么要把轻量对话与知识问答分开

知识问答需要检索、引用和可能的 Chat 模型生成；但问候不需要访问任何企业数据。把两类请求拆开可以减少模型调用和无意义检索，也降低模型把不相关内容当作答案的风险。这是企业 Agent 的重要设计原则：先判定意图，再按最小权限调用工具。

## 4. 面试时可以如何介绍

> 我把 Agent 设计成企业知识与工单协同入口，而不是单纯的 RAG 问答框。前端首轮会先创建临时会话，避免欢迎页和处理中状态叠加，后端完成后再替换成数据库中的正式会话。意图层把问候、知识问答、工单查询和需确认的建单操作分开；只有知识问答才检索资料，只有确认后的建单才写入数据库。这既改善了交互体验，也把工具调用范围和数据写入风险控制在可解释的边界内。

## 5. 验证点

1. 选择工单后，右侧只能显示工单详情；未选择时只能显示空状态。
2. 新会话的第一条消息会立即显示在欢迎页位置，随后显示处理中状态。
3. 发送“你好”返回能力引导，不返回知识库范围不足提示，也没有引用来源。
4. 工单查询和建单的原有权限隔离、确认机制不受影响。
