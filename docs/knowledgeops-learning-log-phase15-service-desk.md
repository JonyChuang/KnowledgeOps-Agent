# 阶段 15 学习日志：待我处理与员工协作边界

## 1. 这次解决了什么问题

前一阶段已经有了“待受理、处理中、待我补充、已解决、已关闭”的状态机，但处理按钮出现在“我的工单”中。这样员工既是申请人又能受理和解决自己的工单，无法体现真实企业中的服务台协作。

本阶段将工单分成两个明确入口：

1. **我的工单**：员工只能查看自己的请求、补充问题、确认已解决，或说明原因后重新打开。
2. **待我处理**：服务人员处理跨员工的队列，可以领取、转派、请求补充和标记已解决。

这样“待受理”不再只是一个没有后续操作的标签，而成为“待我处理”中待领取的真实工作队列。

## 2. 工单处理流程

```text
员工创建
  -> 待受理（服务台待领取）
  -> 服务人员领取
  -> 处理中
  -> 请求补充
  -> 待我补充
  -> 员工补充
  -> 处理中
  -> 服务人员标记解决
  -> 已解决
  -> 员工确认
  -> 已关闭
```

服务人员也可以在未关闭时转派工单。转派不改变当前状态，只改变 `assignee`，因此不会把“谁在处理”与“处理到哪一步”混成一个字段。

## 3. 后端如何保证职责边界

“待我处理”复用 `/api/v1/service-desk/tickets` 接口，必须携带：

```http
X-Actor: service-desk
X-Role: service_desk
```

没有服务台角色时，API 返回 `403`。员工原有的 `/tickets/{id}/status` 通用状态切换接口已移除，不能绕过队列直接把自己的工单改为处理中或已解决。

服务层还继续校验更细的状态规则：只能领取 `open` 工单；只有当前处理人能对 `in_progress` 工单请求补充或标记解决；已解决和已关闭工单不能转派。每个动作同时更新当前工单字段、追加 `ticket_activities` 时间线和 `audit_events` 审计记录。

## 4. 为什么这里还不是完整的生产权限系统

`X-Role` 是用于本地演示和测试的临时标记，浏览器可以自行构造请求头，因此它不能作为真实安全措施。它的价值在于先把接口、服务层和前端职责划分清楚。

生产阶段需要将 `get_service_desk_actor()` 替换为真实登录令牌解析，并引入用户、组织、角色和服务队列成员关系。届时“可处理全部队列”“只能处理自己领取的工单”“可转派给谁”都由数据库角色和队列授权决定，而不是由请求头决定。

## 5. 如何测试

新增 `tests/test_service_desk_api.py`，覆盖完整协作链路：

1. 普通员工请求“待我处理”队列会返回 `403`。
2. 服务人员能在待领取队列看到其他员工创建的工单，并领取后进入处理中。
3. 非当前处理人不能请求补充信息。
4. 当前处理人可转派给网络组；接手人请求补充后，员工补充内容会自动回到处理中。
5. 接手人标记解决后，时间线保留创建、领取、转派、请求补充、员工补充、恢复处理和解决的完整记录。

## 6. 面试时可以如何介绍

> 我把工单状态机进一步落到了企业的角色协作中。员工端和服务台端复用同一张工单与同一条活动时间线，但使用不同的 API 和权限边界：员工负责提交、补充、确认和重开，服务台负责领取、分派、请求信息与解决。后端不允许前端自由改标签，每次动作都校验状态和当前处理人，并同时写当前状态与不可变审计事件。演示版本先用请求头模拟角色，后续能平滑替换为 JWT、组织角色和服务队列授权。
