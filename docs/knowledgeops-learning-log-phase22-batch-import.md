# 阶段 22：知识库批量文件导入

## 问题

原先的本地上传控件只能选择一个文件，而页面虽然写着“点击或拖放文件上传”，实际上没有处理拖放事件。对于 v0.2 的 24 份评测资料，逐个选择、上传和等待索引既慢又容易遗漏。

## 设计

批量导入保留原有的单文件上传 API，不增加一个难以维护的大文件批处理接口。前端一次接收多个 `File`，按照选择顺序逐个上传；上传成功后，再为这一批文档依次提交索引任务。这样每个文件仍有独立的名称、状态、失败原因和“重新索引”入口。

拖放文件与点击“本地上传”共用同一个导入弹窗和同一批处理流程。拖入页面中的上传区域时，文件列表会预先带入弹窗；点击选择文件时，输入框开启多选。

## 为什么不并发上传全部文件

一次并发发送 24 个文件会让浏览器、API 和 Celery Worker 同时承受突发压力，也会让失败重试和进度判断更复杂。顺序上传更适合当前的企业资料导入规模，接口状态也更容易解释。后续如果需要导入数百个大文件，再设计后端任务批次、并发上限和断点续传。

## 验证方式

在知识库详情页点击“本地上传”后，Windows 文件选择框应允许按 `Ctrl + A` 选择全部 Markdown 文件；弹窗中的资料名称会显示已选文件数。也可以在资源管理器中选中多个文件，直接拖到页面上传区域。提交后，页面应出现每份文件的独立索引状态。

## 面试表达

“知识库导入没有只停留在单文件 Demo。前端把多个浏览器 File 复用同一上传 API，逐个落库后再批量提交异步索引，因此每份资料都可追踪、可失败重试。拖放和文件选择共享同一流程，既提升员工导入效率，也不牺牲文档级审计能力。”
