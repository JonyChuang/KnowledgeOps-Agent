# 阶段 17 学习日志：全局搜索、个人工作项与 Agent 反馈

## 1. 本阶段范围

“服务目录”按当前计划跳过。本阶段直接完成三个员工高频功能：

1. **全局搜索**：从一个输入框检索本地知识资料、图谱实体、当前员工历史 Agent 对话和当前员工工单。
2. **收藏与最近访问**：让常用内容不必每次重新查找。
3. **反馈入口**：在每条已保存的 Agent 回答下提交“有帮助、无帮助、引用过期、答案不准确”。

## 2. 为什么搜索先采用本地聚合

知识库的正式问答仍使用 Qdrant、Elasticsearch 和 GraphRAG。全局搜索的目的不同：它是员工的导航入口，需要在外部向量库或模型临时不可用时，依然能发现自己已提的工单、旧对话和已导入资料。

因此 `/api/v1/search` 先按关键词聚合数据库中的资料、当前员工工单和当前员工对话；图谱部分使用已有的规则实体抽取器返回可直接跳转的实体入口。这个实现不替代 RAG 问答，而是让人更容易进入正确的业务页面继续处理。

## 3. 个人数据如何隔离

新增三个表：

| 表 | 记录内容 | 隔离方式 |
| --- | --- | --- |
| `favorites` | 员工手动收藏的工作项 | `(actor, entity_type, entity_id)` 唯一。 |
| `recent_visits` | 最近打开过的工作项 | 同一唯一键只更新时间，不累积重复记录。 |
| `agent_feedback` | 对一条 Agent 回答的当前反馈 | `(actor, agent_message_id)` 唯一，员工可修正自己的反馈。 |

所有读取和写入均带当前 `X-Actor`。搜索中的工单和对话同样按当前员工过滤，不能因为搜索关键词相同而读到其他员工的内容。

## 4. Agent 反馈如何形成维护信号

反馈记录保留答案消息 ID、反馈类型、补充说明和处理状态（`open`、`reviewed`、`resolved`）。当前前端将反馈放在回答下方，员工不需要离开对话上下文；后续知识库管理员可基于这张表建立反馈处理队列、更新来源文档，并把状态推进到已处理。

这一步的核心是先将“觉得回答有问题”的非结构化感受变成可关联、可去重、可审计的业务数据，而不是只弹出一次无法追踪的满意度提示。

## 5. 面试时可以这样介绍

> 我将全局搜索与 RAG 问答分开设计。RAG 负责带来源的知识回答，而全局搜索是容错的工作区导航层，聚合本地资料、图谱实体、个人工单和个人对话，并严格按员工身份过滤。为了提升重复任务效率，我为收藏和最近访问建了独立的员工隔离模型；最近访问采用唯一键加更新时间，避免浏览行为产生大量重复行。Agent 反馈直接绑定持久化回答消息，支持员工修改反馈，后续能自然接入知识库维护队列。
