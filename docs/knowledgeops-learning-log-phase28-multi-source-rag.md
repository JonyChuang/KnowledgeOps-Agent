# 阶段 28：多来源 RAG 证据覆盖

## 本阶段解决的问题

v0.4 多跳评测的 120 条可回答问题中，只有 53 条同时取回了两份所需资料，Evidence Recall@4 为 59.58%。原有 Hybrid RAG 把“同时结合制度和流程”当成一条普通长问题，只做一次整句召回；即使结果来自不同文档，也不能保证每个被明确要求的资料角色都拥有一个证据位置。

这不是用题目关键词给结果加分。企业员工本来就会提出“结合制度和流程”“流程是否有例外”“按手册和政策确认”的跨资料问题，系统需要显式处理这类证据覆盖需求。

## 设计

新增 `knowledgeops/rag/query_planning.py`。当问题中明确出现两种或以上资料角色时，计划器保留原问题，并产生以同一业务主题为中心的聚焦查询：

```text
“结合 VPN 制度和流程处理连接故障”
  -> 原问题：用于总体候选排序
  -> “VPN 连接故障 制度 policy”：寻找制度证据
  -> “VPN 连接故障 流程 procedure”：寻找流程证据
```

目前支持的通用角色为 policy/制度、procedure/流程、exception/例外和 runbook/手册。没有明确多来源要求的普通问题仍只有一次 Hybrid 检索，不增加 embedding 调用和延迟。

`HybridRetriever` 对每个聚焦查询分别进行向量和关键词召回、RRF 融合和可选重排序。最终结果先为每种资料角色保留一份不同文档的证据，再由原问题的全局排名补齐剩余位置。文档仍必须通过既有的 `active` 生命周期过滤；系统不会根据 `archive` 文件名或文档正文猜测资料是否已失效。

## 回答质量

回答提示词要求：

1. 多来源问题按来源分别说明结论和适用范围。
2. 资料冲突、版本差异和例外条件必须明确说明。
3. 资料中出现 `FIELD=value` 这类结构化事实时，原样保留相关字段再解释。

保留结构化字段既让员工能回溯原始制度条目，也避免把“记录负责人和完成时间”这类自然语言改写丢失为不可审计的概述。它不是要求模型输出所有原文，只保留与问题相关的证据。

## 成本和边界

显式多来源问题会比普通检索多进行一到三次聚焦召回，因此延迟和 embedding 调用会增加。这是用有限成本换取跨资料回答的可追溯性；系统只在用户明确需要合并两类资料时启用。

本阶段不自动将名称中包含 `archive` 的文件归档。报告中若仍出现归档资料，应在知识库中把对应文档的生命周期更新为 `archived`，并确认 Qdrant 与 Elasticsearch 的元数据同步成功。这是资料治理操作，不应由检索器猜测。

## 验证

新增测试验证：

1. 普通单跳问题不触发查询扩展。
2. 同时要求 policy 和 procedure 时，检索器选择两个不同来源作为优先证据。
3. 聚焦检索数量与请求的资料角色一致。
4. 回答提示词保留多来源和结构化事实约束。

测试使用内存候选和替身模型，不调用真实 Embedding 或 Chat 服务。

## 面试表达

“我没有把多跳问答等同于扩大 top-k，而是先识别用户明确要求合并的证据角色，再为每个角色执行聚焦召回，并在最终排序中预留不同文档的证据位。这样制度、流程和例外不会被单一高分文档挤掉。回答阶段保留来源和结构化字段，既提高可追溯性，也让离线事实评测能检查真实依据。”
