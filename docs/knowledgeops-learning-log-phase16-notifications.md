# 阶段 16 学习日志：通知中心与可追溯协作

## 1. 这次解决了什么问题

前面的“我的工单”和“待我处理”已经能完成处理流程，但员工仍需要反复打开页面检查状态。真实企业中，受理、转派、补充、解决和关闭都应该主动提醒相关人员；资料索引失败也应反馈给提交人。

本阶段新增“通知中心”。每一条通知都有明确接收人、关联业务对象、已读状态和目标页面。员工打开通知即可跳转到对应工单或文档索引入口。

## 2. 通知从哪里产生

```text
工单受理 / 转派 / 请求补充 / 标记解决 / 调整优先级 / 升级
  -> 通知相关申请人或新处理人

申请人补充 / 确认关闭 / 重新打开
  -> 通知当前处理人

文档解析或索引失败
  -> 通知发起索引的员工
```

同一个动作不会通知操作人自己，避免出现“我刚完成操作，系统又提醒我一次”的无效消息。

## 3. 数据模型如何设计

`notifications` 表保存：

| 字段 | 用途 |
| --- | --- |
| `recipient` | 该通知唯一可见的员工标识。 |
| `type` | 区分工单协作和系统类提醒。 |
| `title` / `content` | 用于列表展示的摘要与详情。 |
| `entity_type` / `entity_id` | 指回工单或文档，避免只依赖文案定位。 |
| `target_view` | 前端应打开的业务页面，例如 `tickets`、`service-desk`、`documents`。 |
| `is_read` / `read_at` | 支持未读徽标、未读筛选和已读审计。 |

工单状态更新、活动时间线、审计事件和通知在同一个数据库会话中写入，然后统一提交。这样不会发生“工单已经变更，但通知漏写”的半完成状态。

## 4. 接口与前端交互

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/api/v1/notifications` | 查询当前员工的通知，支持 `unread_only`、分页，并返回全局未读数。 |
| `POST` | `/api/v1/notifications/{id}/read` | 将一条属于当前员工的通知标记已读。 |
| `POST` | `/api/v1/notifications/read-all` | 将当前员工全部未读通知标记已读。 |

前端侧边栏显示未读数量；通知中心可以切换全部或未读、批量已读。点击工单通知时，前端先写已读状态，再根据 `entity_id` 和 `target_view` 打开“我的工单”或“待我处理”的详情。后端仍通过 `recipient` 过滤，前端不能通过改参数读取其他员工通知。

## 5. 面试时可以如何介绍

> 我把通知中心设计为领域事件的接收人视图，而不是把系统日志直接展示出来。工单动作会先更新工单、活动时间线和审计记录，再在同一事务中写入只属于相关人员的通知。通知保留关联实体和跳转目标，因此前端不需要解析文案来猜测去哪里；同时接口按接收人隔离，支持未读统计、单条已读和批量已读。后续接入 WebSocket、邮件或企业 IM 时，可以继续消费同一类领域事件，而无需改动工单核心状态机。
