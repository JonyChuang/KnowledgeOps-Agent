# 阶段 18 学习日志：让 Agent 支持真实的多轮对话

## 1. 为什么需要这次修正

此前 Agent 的入口是“意图路由”。只有命中知识库问答、查询工单或创建工单等预设意图的消息，才会进入后续工作流；不含关键词的自然语言会被拒绝或只得到固定欢迎语。因此界面虽然叫“智能助手”，实际体验更像一个固定口令入口。

真实企业场景中，员工会先描述问题、补充背景、追问下一步，再在合适的时机查询知识库或创建工单。Agent 需要同时具备两种能力：

1. **通用对话能力**：处理澄清、解释功能、梳理问题和连续追问。
2. **业务工具能力**：在识别到知识库查询、工单查询或创建工单时，调用受限工具而不是编造业务数据。

## 2. 本阶段的设计

### 2.1 路由策略

路由仍然优先保护有副作用的操作：只有明确的创建工单请求才会进入创建工单节点，并且保留用户二次确认。无法映射到业务工具的非空消息统一进入 `general_chat`，不再直接报“无法判断请求类型”。

```text
用户输入
  -> 创建工单意图 -> 准备草稿 -> 用户确认 -> 创建工单
  -> 查询工单意图 -> 只读工单工具
  -> 知识问答意图 -> RAG 检索 -> 基于引用生成回答
  -> 其他自然语言 -> Chat 模型多轮对话
```

### 2.2 聊天模型与上下文

新增 `AgentConversationMessage`，在每次继续已有对话时取最近 8 条已持久化消息，每条最多 1,500 字符，作为 Chat 模型上下文。这两个上限避免单次请求随着历史对话无限增长，同时足以支持常见的连续追问。

普通对话与知识库问答使用同一个 `ChatAnswerGenerator`，但提示词边界不同：

- 普通对话可以帮助梳理问题和说明产品能力，但不得声称已读取内部资料或完成操作。
- 知识库问答只能依据 RAG 返回的引用回答，无法覆盖时必须说明资料不足。

这样“能聊天”不会削弱知识库回答的可追溯性。

### 2.3 工单摘要可读性

工单查询回复不再将 UUID 作为正文主体，改为标题、中文状态、优先级和处理人。UUID 仍保存在 `ticket_ids` 数据字段，供前端跳转和后续工具调用使用。

## 3. 配置与故障提示

自由对话需要 `.env` 中的 `CHAT_MODEL`、`CHAT_BASE_URL` 和 `CHAT_API_KEY`。未配置时，Agent 会明确提示缺少 Chat 模型配置；模型服务暂时不可用时，会提示检查这三个变量和服务连接，而不是表现为“只对固定话术有反应”。

## 4. 验证内容

- `tests/test_agent_chat.py`：验证标准 OpenAI 兼容 Chat Completion 调用、历史上下文传递与知识库引用约束。
- `tests/test_intent_router.py`：验证非业务自然语言进入普通聊天。
- `tests/test_agent_workflow.py`：验证普通聊天不调用业务工具、能够接收历史上下文、工单摘要可读。
- `tests/test_agent_api.py`：验证未配置 Chat 模型时的可理解提示，以及原有工单确认和会话持久化不回归。

## 5. 面试表达

> 我把 Agent 设计为“对话层 + 受控工具层”。普通自然语言由 Chat 模型处理，并携带有上限的已持久化历史上下文；知识问答必须经过 RAG 并基于引用回答；工单查询通过只读工具获得真实数据；创建工单则必须经过 LangGraph 中断节点和用户二次确认。这样既避免了关键词式假 Agent，也避免了模型直接编造企业数据或越权写入工单。
