# 阶段 1 学习日志：员工工作台

## 1. 这一步解决什么问题

原来的系统把“知识库、文档索引、图谱检索、Agent 对话”并列展示，适合开发演示，却不符合员工日常工作方式。员工首先关心的是：我提交的工单有没有人处理、哪些资料正在索引、我下一步可以做什么。

因此本阶段新增“我的工作台”。它不创建新的业务数据，只把已有的工单、知识库和文档索引状态聚合成一个员工可读的入口。

## 2. 员工能看到和操作什么

- 工单进度：待受理、处理中、已解决、已关闭的数量，以及最近五张由当前员工创建的工单。
- 索引健康：知识库数量、已就绪资料、等待处理资料和失败资料数量。
- 常用知识库：最多展示四个最近创建的知识库，点击可进入已有的资料管理页。
- 本次会话：浏览器当前打开期间的 Agent 对话摘要，点击可恢复到对应会话。
- 快捷操作：进入 Agent、知识库和文档索引页。

页面中的“当前操作人”沿用当前项目的 `X-Actor` 演示身份。输入一个名字并点击“查看”，页面就会切换到该员工的工单视角。这是开发演示的临时办法，生产环境会由登录态决定用户身份。

## 3. 后端如何实现

接口是 `GET /api/v1/dashboard`，当前操作人仍从 `X-Actor` 请求头取得。例如：

```http
GET /api/v1/dashboard
X-Actor: alice
```

`DashboardService` 只做查询和计算：

1. `TicketRepository.count_for_requester_by_status()` 使用 SQL 的 `GROUP BY` 按员工统计工单状态。这样不用把所有工单加载到 Python 再计数。
2. `TicketRepository.list_for_requester()` 返回最近五张工单，复用了已有的“申请人只能看自己工单”的规则。
3. `DocumentRepository.count_by_status()` 统计资料的 `uploaded`、`indexing`、`ready`、`failed` 状态。
4. API 路由把 ORM 对象转换为 Pydantic 的 `DashboardRead`，浏览器只获得页面所需字段。

工作台属于**读模型**：它为页面组织数据，却不是新的事实来源。工单事实仍在 `tickets` 表，资料事实仍在 `documents` 表。这样能避免列表页和详情页各维护一份状态、最终互相不一致的问题。

## 4. 为什么本阶段没有数据库迁移

本阶段只增加只读聚合查询，没有新表或新列，所以 PostgreSQL 和 SQLite 都直接使用已有表。后续加入评论、附件、通知、服务目录等真正的新业务实体时，必须新增 Alembic 迁移，不能只依赖本地开发的 `auto_create_schema`。

## 5. Chat 模型的降级设计

本阶段也修复了一个基础问题：以前即使用户只是查询或创建工单，API 也会要求 `CHAT_MODEL` 和 `CHAT_API_KEY`，导致工单工具整体不可用。

现在的行为是：

- 配置 Chat 模型时，使用 LLM 意图路由；知识问答会基于引用生成答案。
- 未配置 Chat 模型时，退回确定性的关键词意图路由；查询工单和“确认后创建工单”仍可使用。
- 未配置模型时发起知识问答，检索完成后会返回明确配置提示，系统不会伪造答案。

这体现了企业 Agent 的一个原则：模型故障或配置缺失时，不依赖模型的受控业务能力仍应可用，同时给出可操作的错误信息。

## 6. 测试如何证明功能有效

`tests/test_dashboard_api.py` 创建一份文档、分别以 `alice` 和 `bob` 创建工单，再请求 Alice 的工作台。测试验证：Alice 只能看到自己的工单统计和最近工单，但能看到当前共享知识库范围内的索引健康状态。

## 7. 当前边界与下一阶段

当前项目仍使用 `X-Actor`，尚未实现登录、组织和角色权限。因此工作台的知识库/索引摘要与原有知识库管理一样处于共享范围，不能当作生产级数据隔离。后续“权限与工作区”阶段会以成员关系校验替换它。

工单目前只有 `open`、`in_progress`、`resolved`、`closed` 四种状态，也没有评论、附件和处理人。下一阶段是“我的工单”：实现独立列表页、状态筛选、搜索、优先级和更新时间；之后再进入工单详情和协同操作。

## 8. 面试时如何介绍

可以这样描述：

> 我没有把 RAG 和 Agent 做成孤立的聊天 Demo，而是让它进入员工日常工作流。首页通过一个只读聚合接口按当前员工汇总工单状态、索引健康和知识库入口；工单数据仍由领域服务负责，工作台只是读模型。同时我把 Agent 运行时拆成“需要 Chat 模型的知识问答”和“不需要 Chat 模型的受控工单工具”，使模型未配置时仍能查询和确认建单，避免非核心模型依赖拖垮整个业务入口。
