# 阶段 4 学习日志：持久化 Agent 会话与工作台恢复

## 1. 这次解决了什么真实问题

原来的 Agent 对话虽然能在当前页面显示，但会话对象只存在浏览器 JavaScript 的内存中。刷新页面后，内存会被清空，所以左侧“最近对话”和工作台“本次会话”都会变成空白。这个实现只能用于静态演示，不能用于员工实际追溯咨询记录。

这次把会话、用户消息和 Agent 回合写入数据库。员工使用同一个操作人重新打开页面时，前端会从 API 加载近期会话摘要；点击摘要后再读取完整消息。工作台读取同一个服务端数据源，因此刷新后也会同步显示。

## 2. 数据模型为什么分成会话和消息两张表

`agent_conversations` 表保存会话级信息：归属操作人、标题、最近更新时间和默认知识库。`agent_messages` 表保存按顺序排列的消息：用户输入、Agent 回答、引用、待确认操作、关联工单和错误信息。

一段对话会包含多次问答，用一张会话表和多张消息表表示是一对多关系。这样可以按会话快速列出历史，也能在打开某段会话时完整还原消息顺序。`conversation_id + sequence` 的唯一约束保证同一会话不会出现重复排序号；每个 Agent 回合的 `turn_id` 也保持唯一，以便确认建单后更新原回合，而不是新增一段互相矛盾的结果。

## 3. API 与前端如何协作

前端发送首条消息时不传 `conversation_id`，后端创建一个持久化会话，再记录用户消息和 Agent 回答。继续同一会话时，前端传回该 ID。新接口是：

```text
GET /api/v1/agent/conversations
GET /api/v1/agent/conversations/{conversation_id}
```

列表接口只返回标题、更新时间、消息数量和最后一条摘要；详情接口才返回完整消息。这种“摘要列表 + 按需详情”的方式避免工作台每次加载都传输大量历史文本。

## 4. 数据隔离与确认操作

会话查询与工单查询一样，始终附带当前 `X-Actor` 条件。Alice 即使知道 Bob 的会话 ID，也会得到 404。确认建单仍由 LangGraph 的 `MemorySaver` 管理短时间内的暂停状态；确认完成后，结果会回写到同一条持久化 Agent 消息中。

因此这里区分了两种状态：数据库保存员工可见、可追溯的会话记录；图状态保存尚未确认的工作流执行上下文。后续做多实例部署时，需要把 `MemorySaver` 换为共享持久化 checkpointer，才能让待确认动作跨 API 重启继续可用。

## 5. 工单详情栏为什么会同时显示空状态和详情

HTML 的 `hidden` 属性本身会让元素隐藏，但 CSS 中 `.ticket-preview-empty { display: grid; }` 的优先级更高，覆盖了浏览器默认的隐藏样式。因此选择工单后，空状态和真实详情会同时显示。

修复是在样式中显式加入：

```css
#ticket-preview[hidden],
#ticket-preview-empty[hidden] { display: none; }
```

这让 JavaScript 的 `hidden = true/false` 状态和界面显示保持一致。

## 6. 如何验证

自动化测试覆盖：

1. 创建对话后能列出并完整读取用户消息和 Agent 回答。
2. 同一会话可以继续提问，刷新后仍有四条按序消息。
3. 其他操作人读取会话时返回 404。
4. 工作台只显示当前操作人的近期会话摘要。
5. Alembic 在全新数据库中创建会话与消息两张表。

## 7. 面试时可以怎样介绍

> 我发现 Agent 对话如果只放在浏览器内存里，刷新后员工无法追溯记录，工作台也无法展示真实活动。因此我把会话抽成主表，把用户消息和 Agent 回合抽成一对多的消息表。前端先拉取会话摘要，用户点开再按需拉取详情；后端按当前操作人隔离所有查询。对需要二次确认的建单操作，确认结果会回写到原来的 Agent 回合，保证页面、数据库记录和工单状态可追溯且一致。
