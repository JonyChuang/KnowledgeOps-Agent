# 阶段 27：Agent 工单受理完整性门禁

## 本阶段解决的问题

v0.4 的 Function Calling 测评中，信息不足时的澄清行为只有 46.67%。问题不在于模型能否生成 JSON，而在于模型有时会把员工没有说过的优先级、分类或影响范围补成草稿字段。字段校验虽然能证明 JSON 完整，却不能证明工单事实完整。

这也是“改进后某些指标看起来更低”的一个原因：检索治理改善的是资料版本和来源多样性；v0.4 新增的多跳回答、澄清行为等更严格指标衡量的是另一条能力链路，不能与单一检索指标直接相加或比较。

## 设计

新增 `knowledgeops/agents/ticket_intake.py`，用一套与业务类别无关的受理规则检查员工消息。准备草稿前，员工至少要给出：

1. 具体问题现象。
2. 可排查的发生场景，例如报错、时间、设备或已尝试操作。
3. 受影响范围或业务影响。

规则只读取员工消息，不把 Agent 的历史回复视为事实来源。这样模型的措辞不会反过来成为“员工已经提供信息”的证据。对于“如何创建工单”这类流程咨询，规则不会误判为真实报修。

## 双层门禁

`TicketIntakeGuardedFunctionCallingAgent` 位于模型调用前。若信息不足，直接返回澄清问题，模型不会获得选择 `prepare_ticket_draft` 工具的机会。这既降低模型调用成本，也避免模型通过工具参数凭空补全信息。

LangGraph 工作流的 `answer_with_function_calls`、`prepare_ticket` 和 `prepare_ticket_draft` 工具执行点再次使用相同检查。这一层用于防止未来替换模型提供商、测试替身或无模型关键词回退时绕过首层门禁。

```text
员工消息 -> 完整性检查 -> 信息不足：澄清并结束
                         -> 信息充分：模型选择草稿工具
                                        -> 员工确认 -> 创建工单
```

人工确认仍然保留。完整性检查解决“能否生成草稿”，确认解决“是否真的写入工单”，两者不能互相替代。

## 验证

新增单元测试覆盖不完整报修、完整报修、跨轮补充信息和流程咨询；工作流测试覆盖无模型回退场景；Function Calling 测试验证信息不足时没有调用模型或草稿工具。现有安全集成测试调整为使用信息充分的建单请求，以继续验证确认前不写入、取消不写入、员工隔离等门禁。

这些测试不调用 Chat 模型，因此可以在本地稳定重复执行。下一次运行 v0.4 时，Function Calling 测评会通过同一前置门禁评估澄清用例；检索和多跳回答指标则应单独阅读，不应把不同层的数字当成同一个分数。

## 面试表达

“我发现 Function Calling 的 JSON 参数校验并不能防止模型补写员工没有提供的工单事实，所以在模型之前增加了通用受理完整性门禁，要求问题现象、排查上下文和业务影响三类事实都来自员工消息。门禁不足时直接追问，不调用工具；充分时才允许生成待确认草稿。随后在工作流和工具执行点复用该检查，形成纵深防御，并用离线 Agent 用例验证澄清行为。”
