# 阶段 25：v0.4 全链路 Agent 测评

## 本阶段解决的问题

v0.3 已经能比较检索方案并测试 Function Calling，但它不能回答三个更接近企业落地的问题：回答是否真正依赖两份资料、信息不足时 Agent 是否会先澄清、以及安全规则是否会在真实 API 调用中生效。

## 设计拆分

本阶段没有把所有结果压成一个总分，而是拆为四层：

1. 困难检索：同一主题下放入制度、流程、例外和归档版本，测试系统能否区分相似资料。
2. 多跳回答：先检索前四条资料，再检查回答是否同时覆盖两份 Gold 资料中的关键事实；无答案问题必须明确拒答。
3. 多轮建单：第一轮信息不足时应追问，第二轮补全信息后才生成草稿。草稿和真正写入工单是两个不同状态。
4. 安全门禁：通过 FastAPI 和临时数据库验证“确认前不写入”“跨员工不可访问”“无服务台角色不可处理工单”等规则。

## 为什么要有 Verifier

主 Chat 模型负责生成回答，Verifier 负责审核回答是否满足 Gold 事实。两者应该使用独立配置，避免出现“模型自己回答、模型自己给高分”的循环。Verifier 也不是绝对真相，因此报告记录它与确定性 Gold 规则的一致率、误放行率和误拒绝率。

## 关键实现

- `knowledgeops/evaluation/answers.py`：从真实 Hybrid RAG 结果构造引用，统计证据覆盖、事实覆盖、拒答和端到端延迟。
- `knowledgeops/evaluation/verifier.py`：调用可选 `VERIFIER_*` 模型，要求返回严格 JSON，并与 Gold 规则结果对照。
- `knowledgeops/evaluation/agent.py`：新增 `clarification_rate`，把“没有调用工具但要求补充信息”与普通闲聊区分开。
- `tests/test_evaluation_v04_security.py`：不访问开发数据库，每次运行创建独立 SQLite 文件，避免安全测试污染本地工单。
- `scripts/run_load_evaluation.py`：统计不同并发下的吞吐、错误率和 P50/P95，而不只看单请求速度。

## 面试表达

“我把 Agent 测评分层设计：检索层用 Recall、MRR、nDCG 和延迟比较不同 RAG 方案；回答层检查多文档证据覆盖、关键事实和拒答能力；动作层测试信息不足时的澄清和信息充分后的草稿生成；安全层用真实 API 集成测试验证确认、角色和数据隔离。这样可以避免只用一个主观总分掩盖具体风险。”

## 当前边界

v0.4 文档和题目仍是脱敏虚构样本，不能替代生产日志。知识库目前没有按员工所有者实施跨知识库授权模型，因此 v0.4 的安全测试只对当前已实现的员工工单隔离、服务台角色和导入防护给出通过或失败结论；跨知识库 ACL 需要作为独立产品能力实现后再纳入强制门禁。
