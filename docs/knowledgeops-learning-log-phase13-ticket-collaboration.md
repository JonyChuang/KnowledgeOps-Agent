# 阶段 13 学习日志：工单协同闭环与标准化建单

## 1. 这次完成了什么

之前的“我的工单”只能按状态筛选、搜索和查看摘要，属于只读列表。这个阶段把它扩展为可追溯的员工协同闭环：员工能查看服务分类、影响范围、优先级、SLA 截止时间、处理人和完整活动时间线；在工单未关闭时可以补充信息；工单被服务团队标记为已解决后，员工可以确认关闭，或者填写原因后重新打开。

同时新增了“创建工单”入口。它不依赖对话框里的自然语言建单，而是提供服务分类、影响范围、紧急程度、标题和描述等标准字段。提交前可以选择知识库调用现有混合检索，显示真实的资料来源；也会在当前员工自己的历史工单中搜索相似问题，帮助减少重复提单。

## 2. 工单数据为什么要拆出活动表

`tickets` 表保存当前状态，例如 `status`、`assignee` 和 `sla_due_at`；`ticket_activities` 表保存不可修改的历史事件，例如创建、补充信息、重新打开和状态变化。两者不能混在一条记录中，因为当前状态只说明“现在是什么”，不能说明“为什么会变成这样”。

时间线每次只追加新记录，不覆盖旧记录。这样员工能追踪问题是否已经补充过信息，服务团队也能在后续接入处理队列时理解每次流转的原因。

## 3. SLA 如何实现

在尚未接入企业 SLA 配置中心前，系统使用透明的默认目标：低优先级 72 小时、中优先级 24 小时、高优先级 8 小时、紧急 2 小时。创建工单时根据优先级计算 `sla_due_at`，详情页直接展示截止时间。

这里的设计重点不是把规则写死为最终生产方案，而是先把 SLA 作为明确字段落库。未来接入服务目录后，可以按“服务分类 + 影响范围 + 优先级”查询策略表重新计算，而不需要改动工单详情接口和页面。

## 4. 权限边界

当前演示环境用 `X-Actor` 表示临时身份。所有员工端接口都坚持 `ticket.requester == actor`：读取详情、补充信息、确认解决和重新打开都会先验证工单归属，不属于当前员工时统一返回 404。

处理人领取、转派、升级和服务团队改变状态没有在这一阶段开放。它们必须先引入真实登录、角色和队列归属，否则只凭前端输入处理人名称会造成越权风险。这些能力将放在“待我处理”阶段实现。

## 5. 提交前建议不是假 AI

知识建议复用已有的 `POST /knowledge-bases/{id}/search` 混合检索接口，结果包含资料来源和真实片段；相似工单复用 `/tickets?query=...`，且仅查询当前员工自己创建的历史记录。没有可用知识库或没有检索结果时，页面会明确显示没有结果，而不会伪造推荐。

## 6. 验证覆盖

聚焦测试覆盖：

1. 创建工单时写入 SLA 和首条活动记录。
2. 请求人补充信息和重新打开后，详情接口立即返回最新时间线。
3. 其他操作人不能评论或读取不属于自己的工单。
4. 非“已解决”状态不能确认关闭或重新打开。
5. 标准化建单接口保存服务分类、影响范围和 SLA。
6. Alembic 能从空数据库创建 `ticket_activities` 表。

## 7. 面试时可以如何介绍

> 我把工单从单纯的列表查询扩展成可追溯的协同对象。当前状态放在工单主表，创建、补充和状态变化以追加式活动表保存，因此详情页能展示完整时间线。员工只能操作自己的工单，确认解决和重新打开都有严格的状态前置条件；处理人分派没有在缺少角色模型时提前开放。创建工单时还复用了已有的混合检索和同一员工的历史工单搜索，给出真实资料和重复提交提醒，而不是在前端写固定推荐内容。

## 8. 发布后的错误提示修正

前端不能直接把后端 JSON 的 `detail` 字段当成字符串。FastAPI 的参数校验失败会返回对象数组，如果 JavaScript 强制转成文本，就会显示 `[object Object]`，用户无法判断问题。现在请求工具会把每个校验项转换为“字段名: 原因”的可读提示。

这不是替代后端校验，而是让后端已经给出的错误信息能正确呈现。界面出现错误时，应同时检查浏览器加载的前端版本和 API 容器镜像是否来自同一次构建，避免新页面调用旧接口。
